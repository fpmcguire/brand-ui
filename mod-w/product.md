## 1. Purpose

`brand-ui` is a small multi-brand shared UI library for Angular, plus a gallery app that shows it.

It has two purposes:

1. **Domain learning.** Model how a digital agency works: several unrelated clients, one shared component base, brand identity applied through design tokens.
2. **Workflow evidence.** Test how MOD-W governs a reusable UI system, in particular the idea that such a system needs a living review surface (MW-OBS-022) and the branch-isolated exploratory build idea (MW-OBS-023). Both observations remain `NOT_YET_TESTED`; this project is one small data point, not a conclusion.

### 1.1 Framing

- The output is a **reference implementation**. It does not go into production and is not retroactively approved by merging or documenting it.
- Brand status, stated plainly:
  - **ArtAnon Shop** is a real business owned by a third party (the Moderator's family). This project is an unofficial **concept exploration** of turning its existing identity into tokens. It is not an official rebrand, and no affiliation or delivery claim is made. Its logo is used only as a design input and is never committed to this repository; the repo holds palette values and a text wordmark only (see A-8).
  - **IT English Mentor** is a new brand for the Moderator's own freelance venture. Its visual direction may later become real.
  - **CodeCraft Academy** is a placeholder name for open-source tech and code examples, in the spirit of the Moderator's published Angular design-pattern examples.
- No other third-party logos, trademarks or client material are used.
- Nothing here claims to be a delivered client rollout.

## 4. Brands

Three brands (see 1.1 for their status), deliberately different on tone, color, type, shape and density. ArtAnon Shop mirrors the common agency case of a client with an existing identity that must be translated into tokens; IT English Mentor is a brand created from scratch. Detailed direction belongs to `design-spec.md`.

| Brand             | Industry                                                               | Direction (from Moderator)                                                   | Priority |
| ----------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------- |
| ArtAnon Shop      | Online art and print shop (real business, third party)                 | Modern, artistic, minimalistic; palette taken from the supplied logo         | Must     |
| IT English Mentor | Freelance English mentoring for IT professionals (Moderator's venture) | Professional, educational, clean                                             | Must     |
| CodeCraft Academy | Open-source tech and code examples (placeholder)                       | Tech-savvy, innovative, vibrant; one brand with Light and Dark styling modes | Should   |

All brands share the same component set and the same semantic token names. Only token values differ. CodeCraft Academy remains one brand: its Light and Dark styling modes use the same token names, typography, spacing and shape, with mode-specific color values. The gallery therefore represents three brands through four rendered scopes: ArtAnon Shop, IT English Mentor, CodeCraft Academy Light and CodeCraft Academy Dark. If a brand needs a different structure, that is a documented component variant, not a one-off.

### 5.1 Non-goals

- Production use, publishing to any public or private registry, or a changelog. Version numbers needed for the v1.1.0 release and installed package archive are allowed.
- Server-side rendering, routing beyond the gallery, internationalization.
- A real CMS, backend or API.
- Storybook. A custom gallery is used; a Storybook comparison is a possible follow-up.
- Nx or any monorepo tooling.
- Visual regression testing, cross-browser matrices, real-device testing. S-18 uses measured production-build and lab figures only.
- A general dark-mode feature across all brands. Dark appearance exists only where a brand needs it.
- Animation libraries, icon libraries beyond what the components need, form frameworks.
- Third-party brand names, logos, photography or copyrighted artwork. The ArtAnon Shop logo is never committed; ArtAnon appears as a text wordmark and palette values only.
- Any claim that this is delivered brand work for ArtAnon Shop, or an official rebrand of any real business.
- Fabricated testimonials, prices, course claims or contact details under a real brand name. Sample content is neutral and labeled as sample.
- Any claim that this project validates MW-OBS-022 or MW-OBS-023.
- A local registry such as Verdaccio unless the Moderator separately promotes it.
- Moving Button or TextInput into the atomic package (S-19).
- New components, including S-10 items, and any change to tokens, brands, scopes or existing Design IDs.
- Any claim that the Atomic Design refactor improves performance, accessibility or maintainability; the repository records only measurements and review findings.

### 5.2 About panel (S-11)

**Why it is wanted.** A first-time reader of the gallery cannot tell what brand-ui is for, what the library is, or how the gallery relates to it. The panel answers that on the page itself, so the gallery is understandable without opening the repository.

**What it is.** A popup dialog owned by the gallery app. It is **not** part of the `ui` library, is not exported from `ui`, and is not one of the four components. The gallery may build its close and reopen controls from library components, and the panel itself consumes `ui` the way any outside consumer would (AC-4).

**Content it must explain** (plain language, short; wording to match the README, AC-12 and AC-17):

1. **The project.** brand-ui is a reference spike, not production software. Its two purposes are domain learning (how an agency serves unrelated clients from one component base) and workflow evidence. No production, client-delivery, rollout or official-rebrand claim.
2. **The brands and their status** exactly as in 1.1: ArtAnon Shop (unofficial concept exploration, no affiliation), IT English Mentor (Moderator's venture), CodeCraft Academy (placeholder name). Three brands across four scopes; Light and Dark are modes of one brand.
3. **The ui library.** What it contains (four components, theme service and theme scope), and the central idea: every brand fills the same semantic token names, components hold no brand values, and switching brand changes tokens only.
4. **The gallery's relationship to the library.** The gallery is a separate review application. It imports the library through its public entry point only, as an outside consumer would. Everything the gallery adds is its own and is not library API: the brand switcher, the persistent hover, focus and active specimens, the token read-outs, the contrast evidence and the Design IDs. The library does not depend on the gallery.
5. **How to use the gallery.** The brand scope switcher and All brands, the Design IDs checkbox, what each panel section shows, and how to reopen the About panel.
6. **How this was built.** State that MOD-W v5.0.1 is a role-separated workflow in which a Moderator (human-in-the-loop) approves each step and plan and a Tech Lead reviews each step before QA; state that Claude Code acted as the Development Team; identify `mod-w/` as the governing-document location; and link to `https://github.com/fpmcguire/mod-w` as the methodology. This is workflow provenance, not a claim that the project validates MOD-W or any MW-OBS observation. The external link opens in a new tab, uses `rel="noopener noreferrer"`, and has the accessible name `github.com/fpmcguire/mod-w (opens in a new tab)`.
7. **Source repository.** Identify the public `brand-ui` GitHub repository and link to `https://github.com/fpmcguire/brand-ui.git`. The external link opens in a new tab, uses `rel="noopener noreferrer"`, and has the accessible name `github.com/fpmcguire/brand-ui (opens in a new tab)`.

**Out of scope for the panel.** Tutorials, installation steps, marketing claims, any ArtAnon logo or third-party asset, external links other than the MOD-W methodology link in point 6 and the `brand-ui` source-repository link in point 7, and any statement that the project validates MW-OBS-022 or MW-OBS-023.

**Top-bar About item (approved 2026-10-19).** The way to reopen the panel is an "About" item in the gallery's top bar. It opens the dialog; it is not a link to another page, and the gallery still has no routing beyond its one page. Whether the item is rendered with the library `Navigation` component (which today supports links, a current item and a disabled item only) or with a library `Button` styled as a bar item is a Tech Lead decision. The Tech Lead must not change the `Navigation` public API or Design IDs without a Moderator decision. If the item is a button, it keeps the accessible name "About" and returns focus there when the dialog closes.

**Open question for the Tech Lead.** The first-visit auto-open puts a dialog over the gallery on a fresh browser. The existing accessibility scan and three Playwright specifications must still exercise the whole gallery. How they do so (seeded storage, dismissal, or another route) is a technical decision, but it must not weaken AC-8 or reduce the three specifications. About-panel checks (AC-17) join the existing specifications rather than adding a fourth.

## 10. End-of-spike decision

The Moderator decides at the end, using the four outcomes from MW-OBS-023:

| Outcome     | When it fits                                                                                                                                                     |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **STOP**    | Must criteria are not reachable at reasonable cost, or the gallery costs more than it reveals. Keep the evidence record, discard the code.                       |
| **REVISE**  | The approach is sound but a specific part (token model, component API, gallery design) needs rework before more is built.                                        |
| **PROCEED** | All Must criteria pass and the evidence below is positive. The code remains a Reference Implementation; production use needs the normal MOD-W gates re-executed. |
| **TRIAL**   | The result is inconclusive; repeat the approach on a different project before deciding.                                                                          |

### 10.1 Evidence kept for MW-OBS-022 and MW-OBS-023

The original-spike evidence log is kept outside the public repo and shaped like a MOD-W observation (observation, evidence, contradicting evidence, limits). It records:

- Which defects the gallery and automated checks revealed that the written documents did not.
- Whether Design IDs in the gallery made review faster or clearer.
- What the gallery cost to build and maintain relative to the library.
- Whether the shared-library decision was made explicitly in `architecture.md`, not by accident.
- What MOD-W caught or missed: review findings, rejected shortcuts, corrected plans.
- What the one-day time box and the QA-once deviation (A-11) cost or saved.
- Limits: one small project, one Moderator, no real client engagement (ArtAnon Shop is a concept exploration, not delivered work).

The repository additionally keeps this extension evidence:

- What MOD-W caught or missed during the refactor, including review findings, rejected shortcuts, corrected plans and any AC-20 edit to an existing assertion.
- What the decomposition cost relative to what it revealed, including the reasoned "not split" list.
- The S-18 before-and-after figures, measurement conditions and limits.
- What per-Step QA cost or caught when A-15 reversed A-11 for this extension.
- The same limits as the original evidence. This extension does not validate MW-OBS-022 or MW-OBS-023.
